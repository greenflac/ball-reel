## 1. Что взято на вход и как нарезано

Источник `assets/driving_selfie.mp4`. Перепроверено этой сменой:

```
$ ffprobe -v error -count_frames -select_streams v:0 \
    -show_entries stream=nb_read_frames,width,height,r_frame_rate,avg_frame_rate -of default=nw=1 assets/driving_selfie.mp4
width=576
height=1024
r_frame_rate=30/1
avg_frame_rate=9150/307
nb_read_frames=305
```

`avg_frame_rate=9150/307` — прямое свидетельство ДЫРОК ВО ВРЕМЕННЫХ МЕТКАХ:
контейнер длится как 307 кадров, а кадров в нём 305. Поэтому резать по времени
нельзя, режем по НОМЕРУ кадра.

ЧИСТОЕ ОКНО 117..204 (88 кадров) — ВЫБРАНО родительской сменой по швам
`fork_looper.cuts` = [74, 83, 96, 116, 204, 219]; эта смена окно не
переискивала, а проверила прибором (ниже).

```
$ ffmpeg -v error -y -i assets/driving_selfie.mp4 \
    -vf "select='between(n\,117\,204)',setpts=N/30/TB" -vsync 0 -an \
    -c:v libx264 -crf 16 -pix_fmt yuv420p work/bench_clean.mp4
$ ffprobe -v error -count_frames -select_streams v:0 \
    -show_entries stream=nb_read_frames,width,height,r_frame_rate,avg_frame_rate,duration -of default=nw=1 work/bench_clean.mp4
width=576
height=1024
r_frame_rate=30/1
avg_frame_rate=30/1
duration=2.933333
nb_read_frames=88
```

ГРАБЛИ, НА КОТОРЫЕ НАСТУПИЛИ И КОТОРЫЕ СТОИТ ЗАПИСАТЬ: `-vsync 0` вместе с
`-r 30` ffmpeg отвергает («One of -r/-fpsmax was specified together a non-CFR
-vsync/-fps_mode. This is contradictory», код возврата 234). Ровные метки
времени на выходе даёт не `-r`, а `setpts=N/30/TB` при `-vsync 0`: кадры
проходят все до одного, а метки перенумеровываются с нуля с шагом 1/30.

РАСХОЖДЕНИЕ, КОТОРОЕ НЕ ПОДГОНЯЛОСЬ: 88 кадров кратно 4 (правило fal), но наше
внутреннее соглашение 4k+1 требует 89. Взято 88 — потому что 89-й кадр (205) уже
за швом 204. То есть соглашение 4k+1 и реальный материал здесь расходятся на
1 кадр, и это записано, а не выровнено.

## 2. Прибор на швы: чистое окно и НЕГАТИВНЫЙ КОНТРОЛЬ (И5)

Распаковка обоих окон строго с `-vsync 0`. Негативный контроль — окно 70..90,
в котором швы 74 и 83 заведомо есть: прибор ОБЯЗАН сказать «есть».

```
$ python3 -c "... ball_reel.fork_looper.cuts(...)"
ЧИСТОЕ ОКНО 117..204 88 кадров
 "outcome": "годно", "cuts": [], "steps": 87, "median": 8.798, "worst": 1.59,
 "note": "резов найдено 0 по 87 переходам (планка 4.0x типичного скачка,
          самый резкий переход 1.59x)"

НЕГАТИВНЫЙ КОНТРОЛЬ 70..90 21 кадр
 "outcome": "годно", "cuts": [4, 13, 18, 19], "steps": 20, "median": 1.5315, "worst": 50.09
```

- ЧИСТОЕ ОКНО: **проверено 87 переходов, швов 0, не смогли 0.** Самый резкий
  переход 1.59x при планке 4.0x — то есть ответ «швов нет» держится при любой
  планке от 1.6x до 4.0x, а не еле-еле пролезает под порог.
- НЕГАТИВНЫЙ КОНТРОЛЬ: локальные индексы 4 и 13 — это глобальные кадры 74 и 83,
  ровно два известных шва. Прибор шевельнулся там, где обязан. Ещё два индекса
  (18, 19 = кадры 88, 89) — ЛОЖНЫЕ ПО СРАВНЕНИЮ С ПОЛНЫМ КЛИПОМ, и причина
  видна числом: в окне из 21 кадра типичный скачок 1.5315, а в чистом окне
  8.798, то есть мера ОТНОСИТЕЛЬНАЯ и на коротком тихом окне порог 4x
  срабатывает от куда меньшего абсолютного скачка. Вывод для пользования
  прибором: `cuts` считать на ПОЛНОМ клипе, а не на огрызке.

CUT_JUMP = 4.0 — ВЫБРАНО (константа модуля `fork_looper`, не наша).

### ДЕФЕКТ ПРИЁМКИ, НАЙДЕННЫЙ ПО ДОРОГЕ: якорь по умолчанию — НЕ ТО ФОТО

`fork_bench_measure.measure(anchor="assets/photoref_profile.jpg")`, а в fal мы
шлём `assets/fork_ref_gym.png`. Это РАЗНЫЕ фотографии и, по мнению нашего же
прибора, разные люди:

```
fork_ref_gym.png против photoref_profile.jpg -> 0.4437, вердикт «не годно»
```

0.4437 > 0.35. Глазами: обе — блондинки, но `fork_ref_gym.png` это фотография
в спортзале анфас, а `photoref_profile.jpg` — генеративная картинка в розовом
платье в саду, три четверти. Значит запуск прибора «как в задании»
(`python3 -m fork_bench.fork_bench_measure work/fal_clean.mp4 work/clean_frames`)
судит выход против ЧУЖОГО якоря и завышает расстояние примерно на 0.44.
Поэтому ниже приведены ОБА якоря, и удобный не выбран.
