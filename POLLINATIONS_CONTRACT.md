# Pollinations — проверенный контракт API (для живого прогона)

Всё ниже помечено `[проверено live]` (реальный ответ от `gen.pollinations.ai`
с ключом `sk_...` из окружения, 2026-08-12) либо `[из доков]` /
`[проверить в новой сессии]`. Считай непроверенное непроверенным.

## Базовое

- Base: `https://gen.pollinations.ai` — `[проверено live]` (пускается прокси).
- Media: `https://media.pollinations.ai` — **отдельный хост.** Был заблокирован
  egress-прокси (403 CONNECT); после вайтлиста `*.pollinations.ai`
  **`upload` работает** — `doctor` даёт 6/6. `[проверено live 2026-08-12]`
- **`GET /openapi.json` (200) — машиночитаемый контракт всего API.** Читай его
  вместо угадывания: параметры, диапазоны, коды ошибок, тип ответа. Это самый
  дешёвый способ проверить форму эндпоинта, не тратя баланс. `[проверено live]`
  Полный список путей включает `/video/{prompt}`, `/video/models`, `/upload`,
  `/media/{id}`, `/v1/images/edits`. **`/v1/videos/edits` НЕ существует** —
  мультипарт-файла для видео нет, значит media-хост для видео обязателен.
- Auth: `Authorization: Bearer sk_...` **или** `?key=sk_...`. Листинг моделей —
  без ключа. `[проверено live]`
- Ключ в окружении: `POLLINATIONS_API_KEY` (`sk_...`, 35 симв). `[проверено live]`
- ⚠️ Ключ **не имеет** права `account:usage` → `/account/usage` и
  `/account/balance` отдают 403. Баланс не прочитать, но **генерация работает**.
  Не пытайся читать баланс как предполёт — проверяй генерацией. `[проверено live]`
- ✅ Зато `GET /account/key` → **200** и работает без `account:usage`:
  `{"valid":true,"type":"secret","name":"demo_instories","permissions":
  {"models":null,"account":null},"pollenBudget":null,...}`. Это единственный
  бесплатный предполёт «ключ жив и не истёк». `[проверено live]`
- Прокси: `HTTPS_PROXY` уже выставлен, CA-бандл `/root/.ccr/ca-bundle.crt`,
  `REQUESTS_CA_BUNDLE` тоже. `requests` ходит сам. При 403 от прокси на хост —
  **не обходить**, это политика (см. `/root/.ccr/README.md`).

## Картинка — text→image и image→image

### text→image `[проверено live]`
```
GET /image/{prompt_urlencoded}?model=flux&width=512&height=512&seed=7
```
→ 200, `content-type: image/jpeg`, тело — байты картинки (синхронно, ~2.6 c).
Параметры (из доков): `model, width, height, seed, quality, image, transparent`.
⚠️ **`nologo` — не существует**, убран из клиента. `[проверено: не в доках]`

### image→image, вариант A — по URL `[проверено live: поведение]`
```
GET /image/{prompt}?model=kontext&image={REF_URL}&width=&height=&seed=
```
Сервер Pollinations **сам скачивает** `REF_URL` со своей стороны. Если URL
недоступен извне — 400 `failed_to_download_image`. В прошлой сессии подсунул
самоссылку на `gen.pollinations.ai/image/...` → она отдала `HTTP 522` при
серверном фетче. **Вывод: `image=` требует реально фетчабельный публичный URL**
(правильный источник — `media.pollinations.ai/{id}` после `upload`).

### image→image, вариант B — мультипарт, БЕЗ media-хоста `[проверено live]` ✅
```
POST /v1/images/edits
  form: model=kontext, prompt=..., size=720x1280
  file: image=@face.jpg
```
→ 200 JSON `{created, data:[{b64_json, revised_prompt}], usage}`, ~7 c.
Картинка в `data[0].b64_json` (base64). **Это предпочтительный путь для
старт-кадра**: лицо грузится прямо в `gen.pollinations.ai` (разрешённый хост),
media-хост не нужен.

⚠️ **`size`/`width`/`height` у `kontext` ИГНОРИРУЮТСЯ — всегда 1024x1024.**
`[проверено live]` Просил `size=720x1280` через `/v1/images/edits` → отдал
1024x1024; просил `width=720&height=1280` через `/image/{prompt}?model=kontext`
→ тоже 1024x1024. (У `flux` через `/image/` `width/height` работают: 512x512
пришло как просили.) Вывод: **вертикальный старт-кадр от kontext не получить**;
9:16 делает уже видео-модель через `aspectRatio` (seedance отдал ровно
720x1280 из квадратного старт-кадра, кадрирование адекватное).

## Видео — image→video `[проверено live]` ✅
```
GET /video/{prompt}?model=seedance-2.0&image={MEDIA_URL}&duration=4&aspectRatio=9:16&audio=false
```
→ **200, `content-type: video/mp4`, тело — сырые байты mp4 синхронно.**
Никакого JSON-джоба и поллинга нет (в `/openapi.json` у 200 объявлен ровно один
тип — `video/mp4: binary`). Ветка поллинга в `video()` не нужна; guard оставлен
как растяжка на случай, если какая-то модель однажды ответит job'ом.

Факты первого живого прогона (seedance-2.0, duration=4, 9:16, старт-кадр по
media-URL): **97 c**, 1 612 283 байт, h264 **720x1280**, 24 fps, 97 кадров,
длительность 4.04 c. `image=` **принял** `https://media.pollinations.ai/{id}`
(сервер фетчит его со своей стороны — ради этого и нужен был вайтлист).
Дешёвая прогонка на `wan-fast` (duration=2): 25 c, 195 КБ, тоже mp4-байты.

### Параметры (из `/openapi.json`, `[проверено live]`)
- `image` — **обычный query-параметр, строка**. Несколько URL разделяются
  `|` или `,`; **`image[0]` = старт-кадр, `image[1]` = конечный кадр** (это
  нотация из доков про элементы списка, а НЕ имена параметров — слать надо
  `image=<url1>|<url2>`). Ошибки: `failed_to_download_image`,
  `invalid_image_url`, `image_too_large`, `unsupported_image_media_type`.
- ⚠️ `duration` — **валидируется по модели, 400 при выходе за диапазон**:
  `seedance-2.0` **4–15 c** (двойка из прошлого плана НЕ прошла бы),
  `seedance-pro` 2–10, `wan` 2–15, `veo` 4/6/8, `nova-reel` 6–120 (кратно 6).
- `aspectRatio` — `16:9` / `9:16`. `width/height` у видео-моделей только задают
  соотношение; тир разрешения — отдельный `resolution` (480p/720p/1080p) и
  только у `veo`, `wan-pro`, `p-video`, `seedance-pro`.
- `audio` — bool, у моделей с `audio_output`. `seed` поддерживает seedance.

### Биллинг — в ЗАГОЛОВКАХ ответа, не в теле `[проверено live]`
Тело — сырой mp4, поэтому `usage` приходит хедерами:
`x-usage-completion-video-seconds`, `x-model-used`, `x-request-id`, `x-cache`.
Клиент складывает их в `pollinations.LAST_VIDEO_USAGE`.

### Модерация: 422 `content_policy_violation` `[проверено live]`
У Seedance **своя модерация поверх Pollinations**, и она режет по формулировке:
```
422 {"success":false,"error":{"code":"content_policy_violation",
 "message":"... (Reason: Seedance 2.0 generation failed: ... ModelError:
  The input or output was flagged as sensitive ... (E005))",
 "details":{"upstreamStatus":400,...}}}
```
Поймано живьём: тот же старт-кадр и тот же по смыслу промт **проходил**, пока в
него не добавили формулировку кадрирования «the body filling the frame / face
large» — после неё стабильный 422. Значит триггер — **фраза, а не человек на
фото**, и повтор того же промта просто сожжёт все попытки.

Отсюда два требования к боевому циклу (оба реализованы в `produce.py`):
1. **422 не должен ронять прогон.** Вызовы генерации обёрнуты в try/except,
   неудача — это одна потраченная попытка с записанной причиной, а не падение.
   Ошибка распознаётся по имени: `content_policy_violation` → «переформулируй»,
   а не «перезапусти с тем же».
2. **Понижение формулировки по шагам** — `VIDEO_FRAMING_STEPS`: каждая
   следующая попытка описывает кадр проще, последняя — голый промт движения,
   который уже проверен как проходящий.

### Модерация зависит от МОДЕЛИ, а не от контента `[проверено live]`
Один и тот же референс (женщина в спортивном топе и шортах на фитболе) при
одном и том же промте:

| модель | результат |
|---|---|
| `seedance-2.0` | **422 content_policy_violation** при любом тексте |
| `wan-fast`, `wan`, `veo`, `happyhorse-1.1` | **200, клип отдан** |

Изоляция проведена: голый промт («She bounces gently on the fitness ball») и
обезличенный («Gentle bouncing motion…») тоже дали 422 — значит **триггерит
картинка, а не формулировка**. Отдельно ловится и текстовый триггер: описание
отклика мягких тканей на прыжок даёт 422 даже там, где всё остальное проходит.
Правило: физику описывать через **мяч и скелет**, не через тело.

**Вывод: смена модели — рабочий обход модерации, GPU для этого не нужен.**

### Loop: `end_frame` — и что делать, если модель его не уважает `[проверено live]`
Тот же старт-кадр, переданный ВТОРЫМ элементом `image=<start>|<start>`, требует
от модели вернуться в исходное состояние. Метрика — **стык, нормированный на
собственный шаг клипа** (`motion.loop_seam`): первый↔последний кадр, делённый на
медианный межкадровый шаг. Порог самонормирующийся, магических пикселей нет.

| прогон | стык / шаг | вывод |
|---|---|---|
| seedance-2.0, start+end | **0.03** | бесшовно |
| seedance-2.0, только start | 0.54 | видимый скачок |
| veo, start+end | **0.17** | бесшовно |
| wan-fast | 0.38 | почти |
| wan / happyhorse | 1.71 / 1.61 | **`end_frame` проигнорирован** |

⚠️ **Поправка к более ранней записи этого файла.** Я писал, что «заявлен ≠
уважается», и это было неверно: `wan` и `happyhorse-1.1` **не заявляют**
`end_frame` — я приписал им лишнее. Сверка списка возможностей с живыми замерами:

| модель | заявляет `end_frame` | замеренный стык |
|---|---|---|
| seedance-2.0 | да | 0.03 ✓ |
| veo | да | 0.17 ✓ |
| wan-fast | да | 0.38 ~ |
| wan | **нет** | 1.71 ✗ |
| happyhorse-1.1 | **нет** | 1.61 ✗ |

Совпадение полное: **`video_capabilities` можно доверять**, в отличие от
`supported_endpoints` в `/v1/models` (те действительно врут). Модель без
`end_frame` молча проигнорирует второй кейфрейм, поэтому её выбор для лупа —
ошибка конфигурации, и роутер её блокирует до траты.

Для не-loop моделей остаётся локальный аварийный выход `motion.trim_to_loop`:
клип обычно всё равно ПРОХОДИТ через позу, близкую к стартовой, поэтому луп —
задача обрезки, а не генерации. Стоит один декод, ноль токенов: wan 1.71 → **0.41**
(сохранено 67% клипа), happyhorse 1.61 → 0.75. Лучше, но планку 0.30 не берёт —
чуда не обещаем.

### Поза как измерение: MediaPipe, локально `[проверено live]`
ArcFace отвечает только за лицо, поэтому «поза референса и результата разные»
гейт не ловил. Инструмент — MediaPipe Pose (33 точки, CPU, без сети и ключа);
в mediapipe 1.x старый `mp.solutions` убран, нужен Tasks API и файл модели
`pose_landmarker_lite.task` (5.5 МБ, качается один раз).

Шкала расстояния между позами (среднее смещение суставов в длинах торса,
после нормировки на бёдра и торс — поэтому «тот же человек, снятый ближе»
НЕ считается другой позой):

| сравнение | расстояние |
|---|---|
| кадр сам с собой | 0.00 |
| та же посадка, отличия в конечностях | 0.04–0.25 |
| разброс **внутри одного клипа** (это движение) | 0.05–0.30 |
| **реально другая поза** (стоя vs сидя на мяче) | **0.67** |

⚠️ **Среднее размывает локальные изменения.** Согнутая рука — это 2 сустава из
12, среднее даёт 0.11, а само запястье уехало почти на длину торса. Поэтому
рядом со средним считается **худший сустав**; именно он и работает на клипах.

Живые числа: старт-кадр у ВСЕХ четырёх моделей позу держит (среднее 0.018–0.043),
а расхождение **накапливается по ходу клипа**. По худшему суставу модели
выстраиваются: **veo 0.13 | wan 0.33 | wan-fast 0.41 | happyhorse 0.49**.
Порядок надёжен, точка отсечки (0.40) — на одном референсе, перепроверяй.

Плюс `limb_consistency`: длина конечности в длинах торса не должна плавать по
клипу. Разброс до 25% нормален (ракурсное укорочение), больше — тело резиновое.
На всех четырёх клипах максимум 0.08–0.12, то есть анатомия держится.

### Чего на публичном шлюзе НЕТ вообще `[проверено live]`
`GET /image/models` + `/openapi.json` + `/video/models`:
- **нет** ControlNet / OpenPose / depth / canny / inpaint — ни моделей, ни эндпоинтов;
- словарь возможностей видео целиком: **`start_frame`, `end_frame`, `audio_output`**.

Значит доступное управление позой — это **референс-картинка**, а не скелет.
Покадрового/суставного контроля (OpenPose-скелет, ControlNet, AnimateDiff)
на Pollinations не существует — **вот это и есть настоящая граница GPU-пути**,
в отличие от модерации, которая решается выбором модели.

Практическое следствие: воспроизводимую траекторию упражнения (например круговое
вращение тазом на фитболе) публичным шлюзом задать нечем — только описанием и
удачей. Для повторяемого движения нужен driving video и покадровая поза
(DWPose/OpenPose → ControlNet/AnimateDiff), а это уже свой стек. Заодно там же
снимается вопрос «поза уехала»: она задана, а не выпрошена. Мерить расхождение
мы теперь умеем (см. выше), задавать — нет.

### Инжекция внешности: текст против референса `[проверено live]`
Фото лица несёт **только лицо**. Всё остальное модель выдумывает, если не задано.
A/B на одном и том же лице:

| рычаг | одежда | телосложение | дрифт лица |
|---|---|---|---|
| kontext, без атрибутов | — | выдумывает | 0.109 |
| kontext + текст атрибутов | ✅ | ❌ **игнорирует** | 0.295 |
| **nanobanana, 2 референса** | ✅ из референса | ✅ из референса | **0.176** |
| seedream5, то же | — | — | 0.752 (лицо потеряно) |

Правило: **текст для того, что модель перерисует; референс-картинка для того,
что не перерисует.** Телосложение — второе. `max_reference_images`: kontext
**1** (мульти-референс невозможен), nanobanana 3, klein/seedream5-pro 10,
seedream5/nanobanana-pro 14, gptimage 16. **Ёмкость ≠ верность**: seedream5
берёт 14 референсов и теряет лицо. Роли назначаются по позиции в промте
(«FIRST image for the face…») — именно это заставило модель не смешивать
референсы.

⚠️ `supported_endpoints` в `/v1/models` у видео-моделей **врут** — там перечислены
только image-эндпоинты, `/video/{prompt}` не упомянут, хотя работает. Не верь
этому полю; верь `/openapi.json` и `/video/models`.

## Media upload `[проверено live]` ✅
```
POST https://media.pollinations.ai/upload   (Bearer)
  multipart:  -F file=@face.jpg
```
→ 200 `application/json`, **реальные поля ответа**:
```json
{"id":"87d2b912-ebb6-406a-9fc0-40e6a9e48c34",
 "url":"https://media.pollinations.ai/87d2b912-ebb6-406a-9fc0-40e6a9e48c34",
 "contentType":"image/jpeg","size":122539}
```
т.е. `id` + готовый `url` + `contentType` + `size` (~1.5 c на 130 КБ).
`GET {url}` → 200, отдаёт байты с исходным content-type, **публично** — именно
поэтому его берёт серверный фетч видео-эндпоинта. Лимит 100 МБ, жизнь 30 дней.
NB: `/upload` и `/media/{id}` есть и на `gen.pollinations.ai` (см. `/openapi.json`)
— если media-хост опять закроют, это запасной путь `[не проверено]`.

## Итог: боевой путь produce — весь проверен живьём ✅

1. `POST /v1/images/edits` (мультипарт, `kontext`, локальное лицо) → старт-кадр.
   **Проверено.** ~7 c, 1024x1024 (размер не регулируется).
2. `POST media.pollinations.ai/upload` → `url`. **Проверено.** ~1.5 c.
3. `GET /video/{prompt}?model=seedance-2.0&image=<media_url>&duration=4` → mp4.
   **Проверено.** ~97 c, 720x1280, 4.04 c, 0.72 pollen.

### Калибровка ArcFace на живых кадрах `[проверено live]`

**Клип A** (тот же человек по всему клипу), 8 кадров, размер лица 111–114 px:
`0.176, 0.177, 0.205, 0.219, 0.362, 0.714, 0.426, 0.221`.
Спокойные фронтальные кадры лежат **0.18–0.22**, всплески 0.36/0.43/0.71 — это
верхняя точка прыжка: лицо повёрнуто и смазано. То есть гейт **по худшему
кадру меряет «видно ли лицо сейчас», а не «тот ли это человек»**, и заворачивает
любой честный прыжок.

**Клип B** (другой прогон), 24 кадра, размер лица **64–86 px**: дистанция
**никогда не опускается ниже 0.36** (0.36–0.68), хотя это один непрерывный дубль.
Полосы «тот же человек» (0.18–0.22) не возникает вообще.

Вывод — **размер лица это конфаундер, а не деталь**. Распознаватель ArcFace
принимает кроп 112x112, поэтому детекция мельче ≈100 px — это уже в основном
апскейл, и дистанции раздуваются. Отсюда три константы в `identity_arcface.py`:
- `MIN_FACE_PX = 100` — ниже кадр **не судится вообще** и идёт в `too_small`.
  «Не проверяемо» — это **не то же самое**, что «другой человек».
- `SAME_PERSON_MAX = 0.35` — по **медиане** судимых кадров (не по худшему).
- `HARD_DRIFT_MAX = 0.6` по `p90` — ловит клип, который **уезжает в другого
  человека к концу**, чтобы медиана этого не замаскировала.
- `MIN_COVERAGE = 0.5` — если судимых кадров меньше половины, вердикт
  NOT VERIFIABLE, а не PASS. Это то, что не даёт «слишком мелкому лицу»
  проходить по умолчанию.

Перепроверка нового гейта на тех же двух живых клипах (без новой генерации):
клип A → медиана 0.220, p90 0.513, покрытие 100% → **PASS** (раньше падал
из-за худшего кадра 0.71); клип B → покрытие 0% → **NOT VERIFIABLE**.

**Отдельный пол для старт-кадра.** Резкий still и кадр видео — разные измерения,
их нельзя мерить одной планкой. Живые старт-кадры 72/78/91/98 px дали
0.253/0.179/0.139/0.130 — узкая полоса, и **именно кадр на 91 px породил
полностью прошедший клип**. Планка 100 px завернула бы заведомо рабочий кадр
(поймано на живом прогоне: два аттемпта подряд отлетели на старт-кадре). Поэтому
`START_MIN_FACE_PX = 70` для стиллов, а `MIN_FACE_PX = 100` — только для кадров
видео, где к мелкому лицу добавляется смаз.

### Следствие для промта — кадрирование решается формулировкой `[проверено live]`
Стратегия `energy_led` («пик прыжка, обе ноги от мяча») уводит человека вглубь
комнаты — оттуда и лицо 64–86 px в клипе B. A/B на `kontext` с одним и тем же
референс-лицом (размер лица / дистанция):

| формулировка кадра | лицо | дистанция |
|---|---|---|
| «голова занимает 1/6 высоты кадра» | 81 px | 0.175 |
| «по колено, мяч у нижнего края» | 85 px | 0.168 |
| **«от макушки до мяча, тело заполняет кадр»** | **98 px** | **0.130** |
| «по пояс, голова 1/5 высоты» | 151 px | 0.053 (мяч уходит из кадра) |
| «крупный план лица и плеч» | 320 px | 0.100 (мяч уходит из кадра) |

**Абстрактные доли кадра модель игнорирует — работает называние крупности.**
Плюс: чем ближе кадр, тем лучше держится идентичность. Но за «по пояс» из кадра
исчезает продукт, поэтому в `produce.FRAMING` зафиксирована самая тесная
крупность, при которой человек всё ещё **на мяче**. Идентичность здесь
load-bearing, так что это требование пайплайна, а не творческая настройка.
