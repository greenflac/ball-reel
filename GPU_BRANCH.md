# GPU-ветка: покадровое управление позой

Проект ветки генерации на своём железе. Написан по итогам живых замеров на
публичном шлюзе (см. `POLLINATIONS_CONTRACT.md`) — граница проведена по фактам,
а не по предположениям.

## Почему ветка вообще нужна — измеренное основание

| что пробовали | результат |
|---|---|
| поза текстом («0.6 подскока/с, амплитуда 0.79») | модель читает как настроение, траекторию придумывает |
| поза картинкой-референсом (`nanobanana`, 3 референса, роли по позиции) | лицо ✅, телосложение ✅, **поза ✗** — `pose_d` 0.59 и 0.65 при пороге 0.25 |
| поза кейфреймами (`image=<start>\|<end>`) | пиннинг **только в узлах**, между узлами догадка модели |
| словарь возможностей видео на шлюзе | целиком: `start_frame`, `end_frame`, `audio_output` |
| ControlNet / OpenPose / depth / inpaint на шлюзе | **отсутствуют полностью** |

Вывод: непрерывного управления позой публичным API не получить ничем. Всё
остальное — лицо, телосложение, сцена, луп, вся верификация — уже закрыто и
на GPU не переезжает.

## Что переезжает, а что остаётся

```
                 ┌──────────────── CPU, стек-независимо (ГОТОВО) ────────────────┐
driving video ──▶│ driving.extract  → DrivingSpec (поза/кадр, каденс, амплитуда) │
user photo    ──▶│ metrics.subject_package → лицо, 3D-телосложение, мимика       │
                 │ + validate(): что НЕ измерено — называется явно               │
                 └───────────────────────────┬──────────────────────────────────┘
                                             │
                                    ┌────────▼────────┐
                                    │  РОУТЕР стека   │  ← единственная новая развилка
                                    └────┬───────┬────┘
                    нужна траектория ────┘       └──── хватает старт-кадра
                             │                              │
                 ┌───────────▼───────────┐      ┌───────────▼───────────┐
                 │  GPU: pose-controlled │      │ Pollinations (готово) │
                 └───────────┬───────────┘      └───────────┬───────────┘
                             └──────────┬───────────────────┘
                 ┌──────────────────────▼──────────────────────┐
                 │ ГЕЙТ (CPU, ГОТОВ, общий для обеих ветвей):   │
                 │ ArcFace · поза · анатомия · луп · движение   │
                 └──────────────────────┬──────────────────────┘
                                        ▼  только ПОСЛЕ гейта
                                     upscale → доставка
```

Ровно один блок новый. Это и есть главный тезис проекта: **дорогая половина
меняется, дешёвая остаётся**, потому что извлечение и верификация с самого
начала писались стек-независимыми.

## Принцип, который нельзя нарушить

**Кондиционирующий экстрактор и проверяющий экстрактор — разные.**

Если позу для ControlNet снимать тем же MediaPipe, которым потом меряем
результат, гейт начнёт подтверждать собственные ошибки: систематический промах
экстрактора попадёт и в условие, и в эталон, и разойтись они не смогут. Поэтому:

- **кондиционирование**: DWPose (COCO-133, точнее на кистях и стопах);
- **верификация**: MediaPipe Pose (уже стоит, 3D world landmarks);
- **идентичность**: ArcFace, и она не участвует в генерации вообще.

По той же причине **апскейл ставится строго после гейта**: апскейлер дорисовывает
детали, и ArcFace на дорисованном лице мерит приор апскейлера, а не человека.

## Стек генерации

Кандидаты в порядке предпочтения; выбор требует бенчмарка на своём железе,
здесь он не проверялся.

| вариант | управление позой | идентичность | VRAM | замечание |
|---|---|---|---|---|
| **Wan 2.x VACE** | video-to-video + pose/depth | reference image | 24–48 ГБ | ближе всего к задаче: и поза, и объекты |
| CogVideoX + ControlNet | покадровая поза | IP-Adapter | 24 ГБ | |
| AnimateDiff + ControlNet (SD1.5) | покадровая поза | IP-Adapter FaceID / InstantID | 12–16 ГБ | дешевле, качество ниже |
| SVD + pose-адаптер | слабее | — | 16 ГБ | для коротких клипов |

Идентичность инжектится адаптером (InstantID / IP-Adapter FaceID / PuLID), а НЕ
файн-тюном на человека: файн-тюн на каждого пользователя не масштабируется и
создаёт артефакт, который потом нечем отличить от настоящей идентичности.

## Интерфейс между половинами

`DrivingSpec` уже несёт трек. К нему добавляется рендер условий:

```
DrivingSpec.track  ──▶  pose_sequence/NNNN.png   (DWPose-скелеты, 1 на кадр)
subject_package    ──▶  identity embedding + reference image
                   ──▶  3D-пропорции для РЕТАРГЕТИНГА скелета
scene/objects      ──▶  первый кадр (мяч, фон, свет)
```

**Ретаргетинг — обязательный шаг, а не опция.** Скелет донора имеет пропорции
донора; подставить его как есть значит попросить тело донора с лицом клиента.
3D-пропорции из `metrics.body_metrics` (плечи/бёдра, длины сегментов в торсах)
дают целевые длины, на которые скелет пересчитывается перед рендером условий.
Именно поэтому измерение в 3D было не косметикой: в проекции целевые длины
неизвлекаемы.

## Чего эта ветка НЕ решает

- **Объекты.** Совместимость по мячу (тот ли, там ли, того ли размера) не
  меряется ни здесь, ни в текущем гейте. Это отдельная незакрытая ось; для неё
  нужен детектор объекта и своя метрика, иначе «полная совместимость» останется
  словами.
- **Разделение камеры и субъекта.** Амплитуда и каденс до сих пор считаются в
  предположении статичной камеры. С driving-видео произвольной съёмки это даёт
  систематическую ошибку.
- **Ракурс лица на входе.** 3D спасло телосложение, но не идентичность: на
  развёрнутом фото `id_drift` вышел 0.55 при визуально том же человеке.

## Порядок работ

1. **Валидация входа** (CPU, без GPU): пригодность фото — ракурс, размер лица,
   перекрытия; отказ до генерации с указанием, что именно прислать.
2. **Ретаргетинг скелета** (CPU): донорский трек → целевые пропорции.
3. **Рендер условий** (CPU): DWPose-последовательность.
4. **Генерация** (GPU): один бэкенд из таблицы, за интерфейсом.
5. **Гейт** — уже готов, менять не нужно.

Первые три пункта делаются и проверяются **без единой GPU-минуты**, на уже
собранных модулях. Это и есть смысл разделения: к моменту аренды железа
неизвестной остаётся ровно одна переменная — сам генератор.
