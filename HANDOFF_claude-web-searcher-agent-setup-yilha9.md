## Оценка решения

**Годно частично.** Разделяю два разных «403», их смешение — главный дефект постановки:

- **403/WAF на целевом сайте** (Cloudflare, антибот). Здесь скилл-ресёрчер действительно
  помогает: он подменяет «сходи curl'ом на сайт» на «спроси поисковый/extraction API».
  Это рабочий класс решения.
- **403 от egress-прокси окружения** (то, что наблюдается тут по clawhub.ai, duckduckgo.com,
  r.jina.ai). Скилл это **не чинит принципиально**: запрет стоит до сети, а не на сайте.
  Лечится только списком разрешённых доменов в окружении (Ц3), и это решение владельца.

Риски конкретно этого способа установки:

- Слаг `web-searcher` не подтверждён (Ц10). Ставить неподтверждённое имя в `~/.claude/skills`
  — значит отдать всем будущим сессиям инструкции неизвестного происхождения.
- Скилл = промпт + скрипты, которые исполняет агент. Установка в `~/.claude/skills` —
  это глобальное доверие во всех проектах, без пина версии и без ревью диффа при `update`.
- Каталог `~/.claude/skills/synced/` уже управляется синхронизацией; ставить туда же
  рядом чужое — источник конфликтов при перезаписи.
- Скилл почти наверняка потребует ключ внешнего API (Brave/Exa/Parallel/SearXNG).
  Без ключа он даст ноль результатов, что по Р1 обязано читаться как «не смогли проверить»,
  а не как «ничего не найдено».

## План внедрения

Ш0. **Разблокировать реестр или отказаться от него.** Попросить у владельца окружения
    добавить `clawhub.ai` в allowlist. Не открыли — ставим скилл из локального файла/репозитория,

    причина: источник недоступен» и делаем Ш3 (свой тонкий скилл) без чужого кода.

Ш1. **Ревью до установки, не после (Ц5, Ц10).** Поставить во временный каталог, не в `~/.claude`:
    `npx clawhub@0.23.3 --dir /tmp/skill-review install web-searcher` (версия CLI пинуется),
    затем прочитать SKILL.md и все скрипты глазами (П3): какие хосты дёргает, какие ключи
    читает из env, что исполняет. Лицензия скилла — отдельно от лицензии CLI;
    `non-commercial`/`research-only` помечать. Установка с `--force` поверх флага
    `isSuspicious` — запрещена.

Ш2. **Ключ и негативный контроль (И5) до подключения.** Завести ключ выбранного поискового API,
    прогнать два входа: (а) запрос, который обязан вернуть результаты; (б) запрос с заведомо
    битым ключом — обязан вернуть «не смогли», а не пустой список. Оба вывода — в отчёт.

Ш3. **Обёртка вместо голого скилла.** Подключать не скилл напрямую, а субагента
    `.claude/agents/researcher.md`, который: имеет только Read/Grep/WebSearch/WebFetch/Bash-curl,
    возвращает три исхода (`найдено` / `не найдено` / `не смогли: <причина, хост, код>`) (Р1),
    печатает рядом `проверено N источников, не смогли K` (Р2), и в каждом ответе даёт URL
    источников. Порядок инструментов — от дешёвого к дорогому (П2): WebSearch → WebFetch →
    внешний API → curl.

Ш4. **Глобальность — осознанно.** Чтобы «в любой сессии»: класть в `~/.claude/skills/<имя>/`
    (не внутрь `synced/`), версию скилла зафиксировать в файле `VERSION` и не запускать
    `clawhub update` без чтения диффа. Телеметрию выключить: `CLAWHUB_DISABLE_TELEMETRY=1`
    в окружении, если не хотим слать slug/owner/version в реестр.

Ш5. **Гейт вместо договорённости (Ц7).** Тест, который дёргает субагента на фиксированном
    запросе с замоканным HTTP (сеть в тестах запрещена, Т4) и проверяет, что при коде 403
    возвращается именно исход «не смогли», а не «не найдено». Мутация константы (Т1):
    поменять маппинг 403 → «не найдено» — тест обязан покраснеть.

## Дополнение: вариант «песочница под ресёрч с полными правами по URL»

Вопрос сессии: развернуть отдельную песочницу с неограниченным сетевым доступом,
чтобы ресёрч ходил через неё.

### Что измерено (И3)

- Политика egress этой среды применяется **на шлюзе**, а не переменными окружения:
  `/root/.ccr/README.md` — «The destination host is not allowed by your organization's
  egress policy for this session. Do not retry or route around it — report the blocked host.»
- Docker в контейнере есть (`/usr/bin/docker`), но по тому же README процессы внутри
  контейнеров **не достают** до `127.0.0.1:35817` и не доверяют CA, т.е. локальная песочница
  даёт не больше, а **меньше** сети, чем сама сессия.
- Chromium предустановлен (`/opt/pw-browsers/chromium`) — headless-браузер на месте.

### Вывод по варианту

1. **Внутри этой среды песочницу «с полными правами» построить нельзя**, а построенная
   вовне и используемая как канал к закрытым хостам — это ровно тот обход, который
   запрещён Ц3 и README прокси. Легальная форма только одна: домен санкционированной
   песочницы вносится владельцем в allowlist окружения, и это заявляется явно.
2. **Полные сетевые права не побеждают WAF.** 403 от Cloudflare прилетает из-за
   IP датацентра, TLS/JA3-отпечатка и headless-фингерпринта, а не из-за отсутствия
   «прав по URL». Песочница решает 403 *политики* и даёт место для настоящего браузера;
   403 *антибота* она сама по себе не снимает.
3. Песочница, которая ходит по произвольным URL по указанию агента, — это поверхность
   SSRF и утечки. Ей нельзя давать репозиторные токены; она возвращает только контент.

### Три варианта, в порядке цена/эффект

- **A. Allowlist 3–5 доменов в окружении.** Минуты, ноль инфраструктуры, работает во всех
  облачных сессиях. Первый шаг в любом случае.
- **C. Коммерческий search/extract API** (Brave / Exa / Parallel / Tavily / Firecrawl):
  WAF уже решён провайдером, в allowlist нужен один домен, инфраструктуры нет.
  **Рекомендация: C поверх A.**
- **B. Своя research-box (VPS) с браузером.** Оправдана только там, где нужны
  авторизованные сессии и сайты, которых API не берут. Требует поддержки, репутации IP
  и всё равно требует A для своего домена.

### Требования к research-box, если делать B

- Узкий HTTPS API (`POST /fetch {url}`), а не общий прокси: общий прокси = тот же обход.
- SSRF-гард: запрет `localhost`, RFC1918, `169.254.0.0/16`, редиректов на них; только http/https.
- Лимиты: таймаут, потолок размера ответа, rate-limit на домен, уважение robots.
- Ответ: `{status, final_url, text, fetched_at, outcome}` где `outcome` ∈
  `ok` / `empty` / `failed:<причина>` (Р1); агрегаты `проверено N / не смогли K` (Р2).
- Ноль секретов репозитория на боксе; отдельный ключ доступа; аудит-лог запросов.
- ToS целевых сайтов проверяется до автоматизации обхода антибота (родственно Ц5).

Агентская часть не меняется: субагент `researcher` из Ш3 и гейт из Ш5 работают
поверх любого из A/B/C — источник подменяется, контракт трёх исходов остаётся.

## Дополнение 2: ВПС как брокер + слой безопасности между брокером и песочницей

Вопрос сессии: ходить через свою ВПС, а между ней и песочницей поставить слой безопасности.

### Главное различение

Слой безопасности защищает **вашу ВПС и песочницу** от того, что прилетит из интернета
и от того, что попросит агент. Он **не отвечает** на вопрос политики egress окружения —
тот про направление «сессия → интернет». Поэтому:

- Если политика узкая просто потому, что allowlist по умолчанию короткий (частый случай) —
  брокер это **чистое, согласуемое** решение: один домен в allowlist, аудит, узкий API.
  Слой безопасности здесь ценен именно тем, что делает заявку на allowlist одобряемой.
- Если политика — сознательная граница контроля данных, брокер **по конструкции** является
  каналом обхода, и никакой слой между ВПС и песочницей этого не меняет. Решает владелец,
  молча строить нельзя (Ц3).

Вывод: слой безопасности — это не замена заявке на allowlist, а её обоснование.

### Измеренные ограничения на протокол брокера (И3, из /root/.ccr/README.md)

Раздел «Not supported through the proxy (report, do not work around)» перечисляет:
gRPC / HTTP-2-only, WebSocket upgrade, **client-mTLS**, certificate-pinned клиенты,
HTTPS на портах кроме 443, raw-TCP. Отсюда жёсткие требования к брокеру:

- только HTTPS/1.1 на порту **443**, обычный публичный сертификат;
- аутентификация — **bearer-токен**, не клиентские сертификаты (mTLS не пройдёт прокси);
- никаких WebSocket/SSE-стримов и gRPC в контракте; ответ — один JSON;
- пиннинг сертификата на стороне клиента не использовать (TLS переterminируется прокси).

### Архитектура из трёх зон

1. **Брокер** (публичный домен, в allowlist). Только он виден сессии. Держит токены,
   квоты, аудит. Сам в интернет за контентом не ходит.
2. **Слой политики** между брокером и песочницей: разбор URL до передачи,
   deny-лист `localhost` / RFC1918 / `169.254.169.254` и прочих metadata-эндпоинтов,
   запрет схем кроме http/https, запрет редиректов в приватные диапазоны (проверять
   **каждый хоп**, а не только исходный URL), лимиты размера и времени, rate-limit по домену,
   общий kill-switch.
3. **Песочница-фетчер**: одноразовый контейнер на запрос, без секретов, без сети внутрь
   вашей инфраструктуры, отдельный egress-IP (изоляция репутации), браузер поднимается
   и умирает вместе с запросом.

### Что слой обязан делать помимо сети

- **Возвращаемый контент помечается как недоверенные данные.** Страница, прочитанная
  ресёрчером, — это вход, управляемый посторонним; без обёртки она становится инструкцией
  для агента (prompt injection). Контракт ответа должен нести признак «это цитата, не приказ».
- Санитизация: вырезать скрипты, ограничить размер, нормализовать в текст.
- Аудит: `session_id, url, final_url, status, bytes, ts` — хранить; это то, что предъявляется
  при согласовании allowlist.
- Исходы по Р1: `ok` / `empty` / `failed:<хост, код, причина>`; агрегаты по Р2.
- Ноль репозиторных и облачных секретов на обеих машинах.

### Цена

Это уже два сервиса, аутентификация, аудит, поддержка IP-репутации и дежурство.
Коммерческий search/extract API (вариант C) — тот же брокер, только эксплуатируемый
не вами, с готовым аудитом и антиабузом, и тоже один домен в allowlist.
**Рекомендация прежняя: C, если не нужны авторизованные сессии на сайтах, которых API не берут.**
Собственный брокер оправдан именно этим случаем — и тогда описанный слой обязателен.
